# ai-check-bot

Telegram-бот-диспетчер задач разработки (аудит/чек, фичи, фиксы,
рефакторинг) по нескольким проектам сразу, с поддержкой нескольких
ИИ-провайдеров (Claude, Codex, Cursor, локальная LLM) и интеграцией с
GitHub.

Open source — единственный из моих проектов, который публичный с самого
старта. Этот README — источник правды по продукту, пишется так, чтобы его
можно было целиком скормить кодинг-агенту как ТЗ.

## Статус

Первый рабочий каркас (v0) на месте: конфиг, БД-слой, провайдер-абстракция
(Claude/Codex/Cursor/локальная LLM) с роутером "Авто", очередь задач,
движок пайплайна с полным Full/Lite ЧЕК и общим пайплайном для
Фичи/Фикса/Рефакторинга/Кастома, реестр находок в .md-файлах, GitHub-модуль,
Telegram-бот со всеми разделами меню, автопроверка по квоте. Юнит-тесты
зелёные (`pytest`).

Патч, который генерирует провайдер (unified diff), после явного
подтверждения человеком ("Да" в 💾 Зафиксить и запушить?) реально
применяется на диск (`git apply`) и коммитится (`git commit`) —
см. `app/tasks/patch_apply.py`. Агент по-прежнему НИКОГДА не коммитит
сам по себе — только по нажатию человеком кнопки подтверждения; self-check
(репозиторий самого бота) сверх этого никогда не пушит автоматически.

Логин для Cursor/Codex теперь можно запустить прямо из бота — кнопка
"🔑 Войти" в Настройках → 🔌 Провайдеры ИИ прогоняет `<CLI> login` и
показывает захваченный вывод (обычно там ссылка/код для браузера). Реальный
статус подключения после этого проверяется отдельно (для Cursor —
`cursor-agent status`; для Codex CLI-логина стабильной non-interactive
команды статуса нет, поэтому его подключение просто не отслеживается
автоматически — это честно показано в UI, а не выдаётся за факт).

Реестр (📜) в боте теперь читает из SQLite-кэша (`Finding`), не из .md
напрямую — кэш синкается перед каждым показом вкладки (если есть локальный
чекаут) и после каждого job'а/переноса находки в Отложено/Never, см.
`app/registry_store/sync.py`. Источник правды по-прежнему сами
chek_open/later/never.md — кэш только ускоряет UI и переживает временное
отсутствие local_path (покажет последнее известное состояние с пометкой).

Full ЧЕК теперь реально дописывает найденные проблемы в chek_open.md
(Step 8b, см. `app/tasks/protocol_full.py` и `app/tasks/findings_parse.py`)
— до этого пайплайн только показывал текст отчёта, реестр оставался пустым
даже после настоящего прогона. Повторный прогон на тех же находках не
плодит дубликаты — увеличивает `attempts` у существующей записи
(`register_or_bump_finding` в `app/registry_store/store.py`).

HANDOVER-паттерн на обрыв по квоте (см. README, "Управление
проверкой/задачей") теперь реально срабатывает: Claude ловит
`RateLimitError`/перегрузку (429/529), Codex и локальная LLM — 429 по
HTTP, Cursor CLI — эвристику по тексту ошибки (`rate limit`/`quota`/`429`
в stderr). Раньше `ProviderQuotaExceededError` существовал только в коде
движка пайплайна — ни один провайдер его не поднимал, пауза по квоте не
триггерилась никогда.

⏸ Пауза на прогрессе теперь тоже настоящая (раньше была только ✖ Отмена):
пайплайн блокируется между шагами до нажатия "▶️ Продолжить", не отдавая
слот в очереди другой задаче.

Скоуп Чека ("Всё" / "ЧЕК всё игнор реестра" / "Файл-модуль") раньше
только показывался в промпте текстом, реально ни на что не влиял. Теперь:
по умолчанию находки, уже помеченные Отложено/Never, не переоткрываются
(checker видит их в контексте и знает, что решение уже принято человеком)
— "ЧЕК всё" явно отменяет это и переоткрывает всё заново; "Файл/модуль"
реально сужает sweep() до указанного подпути (с защитой от выхода за
пределы local_path проекта — путь приходит из текста, который вводит
пользователь). См. `app/tasks/scope.py`.

Роутер "Авто" теперь реально учитывает историю успешности (README:
"история успешности на похожих задачах"), а не только статический
приоритет провайдеров. `app/providers/success_history.py` считает долю
`DONE` среди последних завершённых прогонов (DONE/ERROR/CANCELLED) на
провайдер для этого типа задачи — из таблицы `Job`, не `HistoryEntry`
(она пишется только для успехов, по ней нельзя посчитать долю неудач).
Провайдер без истории на этом типе задачи не наказывается и не
поощряется — роутер просто не переставляет его в цепочке приоритета.

Раздел 🔌 Провайдеры ИИ в Настройках получил "Войти"/"Обновить"/"Отключить"
из README (раньше была только "Войти"): "Отключить" — мягкое, на уровне
`ProviderRegistry` бота (роутер и `connected()` перестают видеть
провайдера), секрет в `.env` не трогается и не может — это не сессия, а
статический ключ/CLI-путь; "Подключить обратно" возвращает видимость.

🐙 GitHub получил экран "🔑 Токен" и предупреждение в списке репо, если
токену ≥30 дней (README: "Автоматическая ротация: напоминание переиздать
токен каждые 30 дней"). Fine-grained PAT не отдаёт дату выпуска через
API, поэтому отсчёт идёт с момента, когда бот впервые увидел этот
конкретный токен (по хэшу — поменяли токен в .env, отсчёт начнётся
заново) — честная оценка, не точная дата, тот же принцип, что у оценки
квоты. Само переиздание — ручной шаг вне бота (создать новый PAT на
GitHub, обновить `.env`, перезапустить бота).

Админка получила рабочие 📢 Рассылку и 🧪 Dry-run (были TODO-заглушками):
рассылка шлёт текст всем известным боту пользователям (`User.tg_id`) и
считает успехи/неудачи (заблокировавшие бота — не падение, просто
`failed++`); dry-run прогоняет ту же чистую логику решения, что и
настоящий тик автопроверки (`app/scheduler/decision.py`,
`decide_autocheck_action`), без единого enqueue — показывает, что бы
запустилось прямо сейчас и на каких проектах, включая честный кейс
"условия совпали, но авточек-проектов нет — по факту ничего не будет".

**Важное исправление безопасности.** До этого момента бот проверял
`ADMIN_TG_ID` только для раздела 👑 Админка — ЧЕК/Фича/Фикс/GitHub/
Провайдеры ИИ/Проекты были доступны ЛЮБОМУ, кто напишет боту в Telegram
(он же может выполнить `git commit`, переключить видимость GitHub-репо,
потратить платную квоту ИИ). Теперь `app/bot/access_control.py` —
единый гейт на уровне группы хендлеров ниже всех остальных: не-владелец
получает "🔒 бот приватный" и дальше ни один хендлер не выполняется.
Если `ADMIN_TG_ID` не задан, бот по-прежнему открыт всем (иначе им
некому было бы пользоваться при первой настройке), но это явно
логируется как предупреждение при первом сообщении.

**Критичный баг данных (был всё это время, найден при аудите).**
Enum-поля (`Job.task_type/status/provider/provider_mode`, `Finding.status/
severity`, `HistoryEntry.*`, `ProviderAccount.*`, `QuotaUsageLog.provider`)
были объявлены как обычный `String(N)` — SQLite прекрасно хранил и читал
строку, но SQLAlchemy НЕ оборачивал её обратно в Python enum при загрузке
в новой сессии. `job.task_type` после `session.get()` в свежей сессии
(а это почти каждое нажатие кнопки в боте — своя сессия на каждое)
оказывался голым `str` без `.value`, что падало `AttributeError` на
первом же реальном использовании — например, в `commit_yes` при попытке
собрать текст коммита. Нашёл интеграционный тест на self-check, который
специально гонял `_apply_and_commit_blocking` через реальный ре-лоад из
БД (как в проде), а не переиспользовал объект из той же сессии, что и
создание (как молчаливо делали более ранние тесты). Исправлено —
`app/db/models._enum_type()` (`sqlalchemy.Enum` с `values_callable`,
чтобы в БД по-прежнему шли те же строчные значения, не имена enum).
Регрессия закрыта `tests/test_enum_columns_roundtrip.py` — по одному
тесту на каждую enum-колонку в проекте.

Бот получил глобальный обработчик ошибок PTB (`app/bot/error_handler.py`)
— раньше его не было вообще: необработанное исключение в любом хендлере
PTB просто логировал в stderr и молчал, юзер видел нажатую кнопку, которая
ничего не сделала, без единого намёка на причину. Теперь чат получает
"❌ Что-то пошло не так", а сама ошибка пишется в append-only ActionLog.
Заодно нашёл и закрыл конкретный кейс, который раньше падал бы именно
так: добавление проекта с уже занятым `repo_full_name` — теперь честное
"⚠️ уже есть в списке" вместо `IntegrityError` в никуда.

Ещё один структурный баг: `JobQueue.is_busy()` считает занятым RUNNING и
PAUSED_MANUAL — правильно для нормальной работы (см. Пауза выше), но
если бот падает или его перезапускают ПОКА job в одном из этих статусов,
запись в БД так и остаётся RUNNING/PAUSED_MANUAL навсегда — процесса,
который её ведёт, больше нет, а is_busy() честно продолжает думать, что
занято, и очередь не двигается уже никогда. `JobQueue.reconcile_orphaned()`
теперь вызывается один раз при старте бота (`app/main.py`) и переводит
такие зависшие задачи в ERROR с понятной причиной ("прервано перезапуском
бота"). PAUSED_QUOTA не трогается — это состояние легитимно переживает
рестарт, его подхватывает `scheduler._resume_tick`.

Удаление проекта (📁 Проекты → 🗑️) оставляло висячие строки в служебной
таблице `job_projects` — SQLite по умолчанию не проверяет внешние ключи
(`PRAGMA foreign_keys` выключен), так что рассинхрон не падал ошибкой,
просто тихо копился, а `job.projects` для затронутого job'а молча
превращался в пустой список. `Project.job_links` (`cascade="all,
delete-orphan"`) чинит это на уровне ORM — теперь чистится независимо от
того, какой именно код удаляет проект.

Автопуш (`GitHubClient.push_commit`) раньше просто звал `git push origin
branch` и полагался на то, что local_path уже как-то настроен на
аутентификацию — но никто и нигде это не настраивал, так что "автопуш"
реально сработал бы только на хосте, где git-креды для конкретного репо
уже были заведены вручную вне бота. Теперь `GITHUB_TOKEN` передаётся
через переменные окружения процесса (`GIT_CONFIG_KEY_0`/`VALUE_0`,
официальный механизм git с версии 2.31), а не через argv — токен не
попадает в `ps aux`, виден только тому же пользователю/root (тот же
уровень доверия, что у остальных секретов в `.env`). Работает для
HTTPS-remote; для SSH-remote (`git@github.com:...`) эта аутентификация
не применяется — fine-grained PAT для SSH и не задуман, там свой
механизм ключей.

`⚡ Закрыть все публичные` (`GitHubClient.close_all_public`) раньше
падала с первым же исключением из `set_visibility` — и если репо №5 из
десяти отваливалось по rate limit или из-за прав именно на этот репо,
все уже закрытые репо №1-4 просто терялись из ответа: пользователь видел
голую ошибку, не список того, что реально успело закрыться, и не мог
понять, что делать дальше — ретраить всё заново рискованно (часть уже
закрыта). Теперь метод возвращает `BatchCloseResult(closed, failed)`:
ошибка одного репо ловится внутри цикла и не прерывает обработку
остальных, а хендлер (`app/bot/handlers/github.py::close_public`)
показывает оба списка и логирует их через `log_action`.

`/start` определял "это первый раз для этого юзера" через in-memory
`bot_data["known_users"]` — множество, которое живёт только пока живёт
процесс бота. После любого рестарта/редеплоя это множество обнуляется,
и вернувшийся пользователь снова видел приветственный онбординг-текст
с кредитом автора, как будто это его первый `/start`. `_ensure_user`
теперь сам возвращает, был ли пользователь только что создан в БД
(источник истины, переживающий рестарт), и `cmd_start` решает, показывать
ли онбординг, по этому флагу, а не по памяти процесса.

👑 Админка → статистика собирала строку так: `"По провайдерам: " +
", ".join(...) or "—"`. В Python `+` считается раньше `or`, так что при
пустом `by_provider` выражение схлопывалось в `"По провайдерам: " + ""`
— непустую (за счёт префикса) строку, которая сама по себе truthy, и
`or "—"` никогда не срабатывал: админ видел голое "По провайдерам: " без
единого символа после двоеточия вместо явного "—", когда задач с
провайдером ещё не было. Собрано теперь в отдельную переменную с явным
`or "—"` до конкатенации.

`scheduler._tick` срабатывает каждые 15 минут и раньше ставил в очередь
новую автопроверку каждый раз, когда условие квоты (Full/Lite из
`decide_autocheck_action`) было истинным — без проверки, нет ли уже
такой задачи в очереди/работе/на паузе. Условие квоты может держаться
часами (пока % не изменится или не пройдёт сброс лимита), так что на
практике очередь копила бы дубликат автопроверки на каждом тике — за
несколько часов десятки одинаковых Full/Lite-проверок одних и тех же
проектов. Теперь `_tick` сначала проверяет, есть ли уже job с
`provider_mode=AUTO` в статусе QUEUED/RUNNING/PAUSED_MANUAL/PAUSED_QUOTA,
и если есть — просто ничего не делает на этом тике; новая автопроверка
ставится только когда предыдущая реально завершилась (DONE/ERROR/
CANCELLED).

Добавлено 6 новых ИИ-провайдеров: Gemini, DeepSeek, Grok (xAI), Groq,
Mistral, OpenRouter. Все они говорят одним и тем же OpenAI-совместимым
Chat Completions контрактом (Bearer-токен + POST `{base_url}/chat/
completions`) — тем же, что уже использовал Codex и локальная LLM, так
что вместо копипасты HTTP-логики в 6 файлов вынесен общий базовый класс
`OpenAICompatibleProvider` (`app/providers/openai_compatible.py`):
auth_status/run_prompt/estimate_quota/429→`ProviderQuotaExceededError`
реализованы один раз, конкретный провайдер (`gemini.py`/`deepseek.py`/
`grok.py`/`groq.py`/`mistral.py`/`openrouter.py`) — это только имя,
base_url и модель по умолчанию. Каждый заводится в `.env` одинаково:
`<ИМЯ>_API_KEY` (обязателен), `<ИМЯ>_MODEL` (опциональный override) и
`<ИМЯ>_WEEKLY_TOKEN_BUDGET` (опциональный, для оценки квоты — как у
Claude/Codex). Все шесть автоматически появляются в ⚙️ Настройки →
🔌 Провайдеры ИИ (раздел строится циклом по `registry.all()`, отдельный
UI-код не нужен) и в `router.DEFAULT_PRIORITY` как хвост фолбэка для
каждого типа задачи — Groq дополнительно поставлен вторым в приоритете
для LITE ЧЕК (после локалки) как ещё один быстрый/дешёвый scout за счёт
LPU-инференса с очень низкой задержкой.

Осознанно не реализовано в этой версии (см. TODO в коде): выполнение
промптов через Codex CLI (сам логин работает, но запросы всё ещё идут
только через OpenAI API-ключ — у codex CLI нет стабильного контракта на
non-interactive exec, который стоило бы хардкодить).

## Что это

Telegram-бот-диспетчер задач разработки по нескольким проектам сразу.
**Не только проверка багов** — это диспетчер любых задач, которые можно
делегировать ИИ: аудит/чек, новая фича, точечный фикс, рефакторинг,
произвольная задача текстом. Бот решает, какой ИИ-провайдер и в каком
режиме тянет задачу, следит за квотами, ведёт реестр находок, интегрирован
с GitHub.

## Типы задач (Task Types)

Тип задачи выбирается **отдельно** от того, кто её выполняет — это два
независимых измерения, не смешивать в коде.

| Тип | Что делает |
|---|---|
| 🩺 Чек/аудит | Существующий протокол ЧЕК на 13 шагов (см. ниже) |
| ✨ Фича | Реализация новой функциональности по описанию |
| 🔧 Фикс | Точечное исправление конкретного бага |
| ♻️ Рефакторинг | Улучшение существующего кода без смены поведения |
| 📝 Кастом | Свободный текст — что угодно, что не попало в категории выше |

Для Фичи/Фикса/Рефакторинга/Кастома вход — обязательный текст-описание
задачи (аналог "комментария" у Чека, только тут это не опция, а суть
задачи). Дальше идёт тот же пайплайн: постановка → исполнение → отчёт →
подтверждение коммита — просто без части шагов протокола ЧЕК, которые
специфичны именно для аудита (fleet-planner, критики и т.д. нужны только
проверке; фиче нужнее просто "спланировать → написать → протестировать →
показать диф").

## Провайдеры ИИ (абстракция, важно для архитектуры кода)

Провайдер — это не просто "какая модель", а отдельный слой с своим
способом авторизации и вызова. Код должен трактовать это как интерфейс
(`AIProvider`), не хардкодить Claude как единственный вариант.

| Провайдер | Как исполняет | Как логинится |
|---|---|---|
| **Claude** (Anthropic) | Opus/Sonnet/Haiku, штатный флот-протокол | API-ключ или сессия Claude Max 5x подписки |
| **Codex** (OpenAI) | codex CLI / API | API-ключ или логин в аккаунт ChatGPT |
| **Cursor** | Cursor Agent CLI (`cursor-agent -p`) | Логин в аккаунт Cursor (уже был как Tier 1 делегирования в старой схеме) |
| **Локальная LLM** | Qwen2.5-Coder на RTX 3060 через Ollama/vLLM | Без авторизации, локальный endpoint |
| **Gemini** (Google) | OpenAI-совместимый endpoint | `GEMINI_API_KEY` |
| **DeepSeek** | OpenAI-совместимый API | `DEEPSEEK_API_KEY` |
| **Grok** (xAI) | OpenAI-совместимый API | `GROK_API_KEY` |
| **Groq** | OpenAI-совместимый API, LPU — очень низкая задержка | `GROQ_API_KEY` |

### Управление аккаунтами провайдеров

- Раздел в боте: **🔌 Провайдеры ИИ** (в Настройках)
- На каждый провайдер: статус (подключен/не подключен/истёк), кнопки
  "Войти" / "Обновить" / "Отключить"
- Логин — там, где у провайдера есть OAuth/CLI-логин, использовать его
  (Cursor, ChatGPT), не просить API-ключ, если не обязательно
- Все секреты — в защищённом хранилище на сервере бота (env / зашифрованная
  таблица в БД), **никогда не как часть переписки в самом боте**
- Ключевое отличие от текущего ручного процесса (когда токен вставляется
  в чат Claude вручную для разовой задачи) — тут логин делается один раз
  через сам бот и переживает рестарт

### Выбор провайдера под задачу

- Ручной выбор при запуске (кнопками: Claude / Codex / Cursor / Локалка / Авто)
- Режим "Авто" — роутер бота сам решает по: типу задачи, доступной квоте
  каждого подключенного провайдера, истории успешности на похожих задачах
- Fallback-цепочка при недоступности провайдера (переиспользует логику
  текущих Tier 1/2/3 из DELEGATION.md, но обобщённо на любой провайдер,
  не только на Claude-флот)

## Режимы аудита (частный случай Task Type = Чек)

**🔴 Full ЧЕК** — провайдер Claude, полный протокол на 13 шагов:
1–4. Реестр открытых проблем → тесты → логи → sweep
4b. Web-research (Sonnet), по триггеру
5. Fleet-planner (Opus) делит проект на домены
6. Fleet-checkers (Sonnet ×N) параллельно, read-only
7. Агрегация + coverage-check
8. Gap-finder (Sonnet)
9. Fixer (Sonnet)
10. Critic-A + Critic-B (Opus ×2), параллельно
11. Convergence loop, до 3 раундов
12. Test-writer (Sonnet) + обязательный stash-check
13. Human confirm + commit — **агент никогда не коммитит сам, независимо
    от провайдера**

**🟢 Lite ЧЕК** — Sonnet-оркестратор + локальная LLM вместо флота,
эскалация на Full по кнопке.

## Управление проверкой/задачей

- Мультивыбор проектов (включая репозиторий самого бота — self-check по
  умолчанию в списке)
- Скоуп для Чека: всё / "ЧЕК всё" (игнор реестра отложенного) / файл-модуль
- Комментарий/описание задачи перед запуском
- Прогресс — одно редактируемое сообщение, `% = завершённые шаги / всего`,
  кнопки Пауза/Отмена
- Очередь задач (SQLite), если что-то уже выполняется
- HANDOVER при обрыве по квоте — задача на паузу, доезжает сама после
  сброса лимита выбранного провайдера

## Отчёт и действия

Северность (для Чека): 🟥 КРИТИЧНО · 🟧 ВЫСОКИЙ · 🟨 СРЕДНИЙ. Для Фичи/Фикса —
статус тестов + `git diff --stat` + короткое summary что сделано. Кнопки:
Фикс всё / Фикс выборочно / Отложить / Не баг / Детали / OK. Диф —
постранично. Коммит — всегда подтверждение человеком, пуш через
GitHub-модуль.

## Автопроверка по квоте (выключена по умолчанию)

- < 60% недельной квоты выбранного провайдера осталось → сразу Full ЧЕК на
  всех авточек-проектах, высший приоритет
- Иначе < 1ч до сброса И < 90% использовано → Lite ЧЕК на всех
- % квоты — оценка бота по собственным логам расхода per-provider,
  официального API учёта у Anthropic/OpenAI/Cursor для этого нет

## Реестр находок

Источник истины — `chek_open.md` / `chek_never.md` / `chek_later.md` в
каждом репо. SQLite в боте — кэш для UI, синк через GitHub API после
каждого коммита. Доступ — глобально и из настроек каждого проекта, три
вкладки со счётчиками, карточка находки с историей попыток и ссылкой на
файл в GitHub.

## GitHub-интеграция

Fine-grained токен, хранится один раз в `.env`/защищённом хранилище, не в
переписке. Scope: Contents (rw) + Administration **только под смену
видимости**, без `delete_repo`. Функции: список репо со статусом,
открыть/закрыть видимость, issues, батч "закрыть все публичные", пуш
после Step 13.

**Жёсткое ограничение уровня кода, не просто UI-запрет**: удаление
репозитория и истории коммитов недостижимо ни через один путь в
кодовой базе — ни через бота, ни через провайдер-абстракцию.

## Нефункциональные требования

- Секреты всех провайдеров (Claude/Codex/Cursor/GitHub) никогда не
  логируются в открытом виде и не попадают в текст сообщений бота
- Human-in-the-loop на коммит — обязателен независимо от того, какой
  провайдер исполнял задачу
- Self-check (репозиторий самого бота) не автопушит без ручного
  подтверждения, даже если для остальных проектов автопуш разрешён —
  риск оборвать себя же посреди применения патча

## Установка

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env  # заполнить токены
python -m app.main    # запуск бота (long polling)
```

Для разработки/тестов: `pip install -r requirements-dev.txt && pytest`.

Для self-check сценария (бот может закоммитить патч в свой же код —
процессу Python не перезапустить себя штатно) — запускать через
`scripts/supervise.sh` вместо голого `python -m app.main`: это
auto-restart loop, поднимающий бота заново при падении.

Через Docker:

```bash
docker build -t ai-check-bot .
docker run -d --env-file .env -v ai-check-bot-data:/bot/data ai-check-bot
```
